# Voyome — Health & Quality Audit

**Date:** 2026-08-16
**Scope:** Full-repo read-only audit per kickoff brief. No code, config, dependencies, database, or infrastructure were modified during this pass.
**Branch:** `audit/health-check` (read-only; no commits made)

---

## A. Executive summary

Voyome is a small, coherent codebase for what it is: a client-rendered Next.js App Router app that talks to Supabase directly from the browser, with a handful of Next.js API routes reserved for secret-holding integrations (email via Resend, image search via Pexels, account deletion via the service-role key). The build is clean, TypeScript compiles with zero errors, and the architecture is consistent rather than accidental — RLS and Postgres RPCs are the real authorization boundary, not the Next.js layer.

That said, this pass found one **confirmed, currently-live security vulnerability** (an unauthenticated email-sending endpoint that can be used to relay attacker-crafted HTML email from Voyome's verified domain) and a **likely private-data exposure** (journal images sit in a public storage bucket with guessable URLs, despite a "private" flag in the database). Both map directly to unchecked items already listed in `STORE_READINESS.md` Phase 3, so this audit mostly confirms and sharpens known gaps rather than surfacing surprises.

On the reliability side, the offline-sync subsystems (itinerary and packing) are the most fragile part of the app: one confirmed data-loss bug (conflict resolution discards *all* pending offline edits, not just the conflicting one) and one silent-failure bug (packing sync retries permanently-failing mutations forever with no user-visible indicator). There's also a non-transactional money-integrity bug in expense editing that can desync the displayed total from the displayed balances.

The dead-code sweep confirmed what the brief hinted at: `app/trips/[id]/pack-list/` (10 files) is the old v1 packing implementation, fully superseded by `features/packing/` + `app/trips/[id]/packing/` in a May 2026 "packing v2" commit series, and is no longer linked from anywhere in the app.

`npm audit` reports 14 vulnerabilities (13 high), but tracing each one's dependency path shows none are currently reachable through user-supplied input in production — they're concentrated in build-time tooling (ESLint, Tailwind's PostCSS, the PWA build's Workbox/webpack chain) or in code paths the app doesn't exercise (Supabase Realtime is never used, `next/image` is never used). The one genuinely actionable item is bumping the direct `next` dependency itself.

Overall: a live, working product in reasonable shape for its stage, with a short list of concrete, fixable issues rather than systemic problems. Nothing found here suggests a rewrite or architectural overhaul is warranted.

## B. Architecture map

### Client/server split
Every route under `app/` is a `"use client"` page — there are **no React Server Components doing data fetching** and **no `"use server"` actions** anywhere in the codebase. The app is effectively a client-rendered SPA hosted on the App Router. Only 5 files run server-side: the `app/api/*/route.ts` handlers.

### Supabase access
- `lib/supabase.ts` exports a single module-level **anon-key browser client**, imported directly into ~19 client files (pages, hooks, `services/trips.ts`, `features/packing/lib/*`). All trip, booking, packing, journal, and cost-sharing CRUD goes straight from the browser to Supabase through this client — no server layer in between. Authorization is enforced entirely by **RLS policies and Postgres RPC functions**, confirmed to actually enforce access (not just client-side filtering — see Security section).
- A second, separate **service-role client** is constructed only in `app/api/delete-account/route.ts`, the sole privileged server-side Supabase usage in the app.

### Auth flow
No `middleware.ts`, no global auth context/provider, no `onAuthStateChange` listener anywhere. Each protected page independently calls `supabase.auth.getUser()` in a `useEffect` on mount and redirects to `/login` if unauthenticated. This means protected page *shells* (JS/HTML, no data) are servable to logged-out requests — an accepted pattern for this architecture since RLS gates the actual data, but it does mean the auth-check-and-redirect logic is duplicated per page rather than centralized.

### Routing
- Static-ish: `/`, `/login`, `/forgot-password`, `/reset-password`, `/account`, `/invite`, `/support`, `/terms`, `/privacy`, `/offline`.
- Dynamic: `app/trips/[id]/` with sibling sub-routes for `cost-sharing`, `journal`, `pack-list` (legacy, see Dead Code), and `packing` (+ `packing/personalize/*`, thin wrappers around `features/packing/components/*`).
- `app/trips/[id]/` is a self-contained module with its own `components/`, `hooks/`, `lib/`, `types.ts`, and route-local `api.ts` data-access layer, rather than reusing top-level `services/`.

### Data flow (trips)
`services/trips.ts` and `app/trips/[id]/api.ts` are pure client-side Supabase wrapper functions. Multi-step or privileged operations (create trip, transfer ownership, leave trip, remove collaborator) go through Postgres RPC functions (`create_trip_with_owner`, `transfer_trip_ownership`, `leave_trip`, `archive_trip_member`, `revoke_trip_invite`, etc.) rather than API routes. The only place a trip-creation flow touches a Next.js API route is for side effects requiring secrets: sending the invite email and fetching a Pexels cover image.

### State management
No global state library, no Context providers. All state is local `useState`/custom hooks. Two independent **offline-first mutation queues** exist, both localStorage-backed (no IndexedDB anywhere):
1. **Itinerary/bookings** (`app/trips/[id]/hooks/useTripBookings.ts`) — optimistic writes, a replayable mutation queue, and genuine optimistic-concurrency conflict detection via `baseUpdatedAt`.
2. **Packing** (`features/packing/lib/packing-offline-service.ts` + `packing-sync-queue.ts`) — optimistic local cache writes with a retry queue.

Online/offline detection (`navigator.onLine` + event listeners) is independently reimplemented in three places (`OfflineBanner.tsx`, `app/page.tsx`, `useTripBookings.ts`) rather than shared.

### PWA
`next-pwa` (Workbox-based) generates `public/sw.js` + `public/workbox-*.js` at build time from `next.config.ts`'s `withPWA` config, with `/offline` as the document fallback. Registration is manual and production-only via `app/register-service-worker.tsx`, mounted in `app/layout.tsx`. `public/manifest.json` and Apple PWA metadata are present and standard.

### Email / external integrations
`resend` is used in two route handlers (`send-trip-invite`, `send-welcome-email`), each instantiating its own client. Pexels and a weather API are proxied through two more API routes to keep their keys server-side. All 5 API routes are Route Handlers with no `"use server"` actions involved.

**Summary**: the mixed API-route/direct-Supabase pattern is architecturally consistent, not accidental — Next.js server code is reserved for secret-holding integrations; everything else is RLS-gated direct-to-Postgres. The main structural risk this creates is that every "backend" authorization decision lives in Postgres, but (see Security section) the tracked SQL migrations don't cover the full live schema, so parts of that authorization logic aren't auditable from the repo alone.

## D. Findings

### High

**D1. Unauthenticated email-sending endpoint enables open relay + HTML injection from Voyome's verified domain**
- **Location**: `app/api/send-trip-invite/route.ts`
- **Description**: The route has no session/token verification and no check that the caller has any relationship to the trip being referenced. `tripTitle` (fully user-controlled — it's a trip's title) is interpolated unescaped into the HTML email body.
- **Evidence**: Route reads `email`, `tripTitle`, `inviterName` straight from the POST body with no auth check; sends via Resend `from: "Voyome <hello@voyome.com>"`.
- **Impact**: Anyone can POST arbitrary `email`/`tripTitle` and cause Voyome's own domain to send an attacker-crafted HTML email to any address, with no rate limiting. This is both a spam/abuse vector against arbitrary third parties and an HTML-injection-enabled phishing vector riding on Voyome's domain reputation. Directly matches the unchecked STORE_READINESS.md item "Invite flow abuse/rate-limit reviewed."
- **Confidence**: Confirmed.
- **Remediation**: Require a valid Supabase session bearer token; verify the caller via `auth.getUser(token)`; confirm the corresponding `trip_invites` row exists and belongs to a trip the caller can access before sending. HTML-escape `tripTitle`/`inviterName`. Add basic rate limiting.
- **Risk of fix**: Low — additive check in an isolated route; test the legitimate invite flow afterward (this touches a Phase-1 STORE_READINESS test item, "Invite traveller tested").

**D2. Journal images stored in a public bucket with guessable URLs, despite a "private" visibility flag**
- **Location**: `app/trips/[id]/journal/page.tsx` (upload path), storage bucket `journal-images`, migration `202506230003_remove_public_journal_image_listing_policy.sql`
- **Description**: Uploads go to `${tripId}/${Date.now()}.${ext}` in a public bucket. A prior migration removed the bucket's public *listing* policy but its own comment notes objects remain fetchable by anyone with the URL — there's no read-side auth/RLS check.
- **Evidence**: `getPublicUrl()` call confirms public bucket; migration's own comment acknowledges the gap; `trip_id` is a small sequential integer and the filename timestamp is coarse, making path guessing plausible rather than purely theoretical.
- **Impact**: Journal images marked "private" in the database are not actually access-controlled at the storage layer. Real user photo data could be enumerated/guessed by an unauthenticated party.
- **Confidence**: Likely vulnerability (matches unchecked STORE_READINESS.md item "Storage permissions reviewed").
- **Remediation** (additive): switch `journal-images` to a private bucket, serve via server-issued signed URLs after an access check, or add a storage RLS SELECT policy scoped to trip collaborators. Leave existing public objects as-is until rotated — this should get its own migration plan and QA pass per the audit brief's own safety rules.
- **Risk of fix**: Medium — changes how images are served to legitimate users too; needs its own QA pass (flagged per brief section on high-risk changes).

**D3. Itinerary conflict resolution discards *all* pending offline edits, not just the conflicting one**
- **Location**: `app/trips/[id]/hooks/useTripBookings.ts` (`refreshItineraryAfterConflict`), wired from `app/trips/[id]/page.tsx`
- **Description**: When a stale offline edit is detected (`updated_at` mismatch), the only recovery path (`refreshItineraryAfterConflict`) clears the *entire* local mutation queue and refetches from the server — not just the one conflicting mutation.
- **Evidence**: `writePendingMutations([])` unconditionally empties the queue; the UI banner text doesn't warn that other pending offline changes will be discarded.
- **Impact**: A user with several offline edits queued who hits one conflict loses all the others silently. Real data loss.
- **Confidence**: High.
- **Remediation**: Only clear/replay the specific conflicting mutation(s); surface exactly what will be discarded before the user confirms.
- **Risk of fix**: Medium — this is core offline-sync logic; needs a dedicated QA pass against real offline scenarios (STORE_READINESS.md already lists "Conflict recovery tested" as an open Phase-1 item).

**D4. Packing offline sync retries permanently-failing mutations forever with no visible indicator**
- **Location**: `features/packing/lib/packing-offline-service.ts`, `packing-sync-queue.ts`
- **Description**: Any error from a sync attempt — network failure or a permanent error like an RLS denial — is treated the same way and re-queued indefinitely. `getPendingPackingMutationCount()` is exported but never called from any UI.
- **Evidence**: Catch-all error handling in `executeOfflineAwarePackingMutation`; grep confirms the pending-count function has zero call sites.
- **Impact**: A user can accumulate permanently-stuck, never-synced packing changes with zero visibility, indefinitely, while local state silently diverges from server truth.
- **Confidence**: High.
- **Remediation**: Distinguish retryable (network) from permanent (application) errors; surface a "N changes not synced" indicator using the already-existing count function.
- **Risk of fix**: Low-medium — isolated to the packing sync module.

**D5. Expense participant update is not transactional — can leave an expense with zero participants**
- **Location**: `app/trips/[id]/cost-sharing/api.ts` (`updateExpense`)
- **Description**: Updating an expense's participants does a delete of all `expense_participants` followed by a separate insert. If the delete succeeds and the insert fails, the expense is left with the new amount/currency but no participants.
- **Evidence**: Two sequential network calls with no wrapping transaction; `calculateGroupedSummary` silently skips zero-participant expenses in balance calculations while `totalCostByCurrency` still counts them — producing a real mismatch between the displayed total and the displayed balances.
- **Impact**: Money-integrity bug; the failure window requires a mid-sequence network error, so frequency is likely low, but the blast radius (wrong balances) is high-trust-impact for a cost-sharing feature.
- **Confidence**: High (code-level); medium on real-world frequency.
- **Remediation**: Wrap the delete+insert in a Postgres RPC/transaction — the codebase already uses this pattern elsewhere (`202506_create_trip_rpc.sql`, `202501_owner_transfer.sql`).
- **Risk of fix**: Low-medium — self-contained to the expense-update path.

### Medium

**D6. Unauthenticated `/api/send-welcome-email` — lower-severity open relay**
Same missing-auth pattern as D1, but content is static (no injection risk). Still allows spamming arbitrary inboxes with Voyome-branded mail at volume. **Remediation**: tie the call to the just-completed signup's session token; rate-limit.

**D7. RLS policies and SECURITY DEFINER function bodies for core tables aren't in tracked migrations**
The 13 migrations in `supabase/migrations/` cover *changes* to policies/grants but not the original CREATE statements for functions like `remove_trip_collaborator`, `leave_trip`, `archive_trip_member`, `revoke_trip_invite`, nor the base RLS policies for `trips`, `trip_invites`, `trip_collaborators`, `bookings`, `profiles`. This means git is not the full source of truth for the live schema — some of it was evidently created directly against the database outside this tracked history. **Impact**: can't fully verify from the repo whether e.g. `remove_trip_collaborator` checks that the caller is specifically the trip owner. **Confidence**: architectural concern. **Remediation**: pull a full schema dump into the migrations folder (read-only `supabase db pull` or dashboard export) so tracked history matches production, then review each SECURITY DEFINER function body — this directly satisfies the STORE_READINESS.md TODO "Remaining SECURITY DEFINER functions reviewed one by one."

**D8. Expense amount parsing likely breaks for comma-decimal input**
`app/trips/[id]/cost-sharing/components/ExpenseForm.tsx` uses a free-text field parsed everywhere via plain `Number(amount)`. `Number("12,50")` is `NaN`. The app's own UI strings (`getExpenseIcon` matching "middag", "frokost", "øl", "vin", default currency NOK) strongly suggest a Norwegian/Scandinavian user base, where a comma decimal key is the natural input. **Confidence**: medium-high (inferred, not device-tested). **Remediation**: normalize `,`→`.` before parsing, or use a locale-aware parser.

**D9. `use-packing-preferences.ts` — uncaught `JSON.parse` + a genuine flash-of-wrong-content bug**
`features/packing/hooks/use-packing-preferences.ts` has no try/catch around `JSON.parse(saved)` for activities (every other localStorage read site in the codebase wraps this safely — this is the outlier and would crash on corrupted storage). Separately, `packingPreference` is hardcoded to `"Balanced"` and only corrected from localStorage inside a `useEffect` after mount, causing a real flash of the wrong value on load — the same file's `laundry` field avoids this by using a lazy `useState` initializer instead, proving the fix pattern is already established in the same file. **Confidence**: high. **Remediation**: wrap the `JSON.parse` in try/catch; switch `packingPreference` to the lazy-initializer pattern used for `laundry`.

**D10. Duplicate/conflicting `Trip` type definitions**
`types/trip.ts` and `app/trips/[id]/types.ts` both define a `Trip` type that has drifted — the former is missing `user_id` and `currencies`, both actively used elsewhere. `tsc` passes today only because nothing outside `app/trips/[id]` reads `.currencies`; a future edit to one won't propagate compile-time safety to the other. **Remediation**: consolidate to one type.

**D11. Two fully parallel packing implementations coexist in production**
`app/trips/[id]/pack-list/` (v1, orphaned — see Dead Code section) duplicates the business logic and data model of `features/packing/` (v2, live). Beyond being dead code, this doubled the bug surface directly (see D9's sibling issue, D12 below) and represents real ongoing maintenance risk if not removed. **Remediation**: remove after confirming with product (see Dead Code section).

**D12. `usePackingList.ts` load effect has no stale-response guard**
`app/trips/[id]/pack-list/hooks/usePackingList.ts` — an async load effect keyed on `[tripId, activeProfileId]` has no abort/ignore guard; fast profile switching could let a stale response overwrite a different profile's data. **Note**: this hook lives entirely in the orphaned `pack-list` route (D11 / Dead Code), so real-world exposure is currently near-zero, but the bug is real if the route is ever kept. **Confidence**: medium.

**D13. Dependency: direct `next` version has multiple patched CVEs**
`next@16.2.3` is installed; `next@16.3.1` has patches for the DoS/middleware-bypass/cache-poisoning/XSS advisories currently flagged. See Dependency Assessment for full reachability analysis — this is the one broadly actionable item from the 14 `npm audit` findings.

### Low

**D14. `app/api/pexels-destination-image/route.ts` has no top-level try/catch**, unlike all 4 sibling API routes, which either wrap fully or always return a graceful fallback. A malformed body or Pexels network hiccup throws an unhandled exception → generic 500 instead of the `{ imageUrl: null }` shape used elsewhere. Low blast radius (only affects a hero image). **Remediation**: wrap in try/catch to match sibling routes.

**D15. `send-trip-invite` interpolates `tripTitle` unescaped into email HTML** (same code as D1 — `inviterName` is currently hardcoded to `"Someone"` at both call sites so it's not attacker-controlled today, but `tripTitle` is fully user-controlled). Narrow phishing/content-injection vector via a trusted sending domain. Bundle the escaping fix with D1's remediation.

**D16. `delete-account` cascade behavior unverified from the repo**, and both the route and its client caller (`app/account/page.tsx`) lack try/catch — a route exception produces an unhandled crash instead of the route's own error shape, and a client-side network failure leaves the delete spinner stuck with no message. The authorization logic itself is correctly scoped (verified caller can only delete their own account). **Remediation**: add try/catch on both sides; confirm `ON DELETE CASCADE` behavior against the live schema for user-owned tables (trips, expenses, bookings, packing data, journal entries).

**D17. `openConfirm(config: any)`** in `app/trips/[id]/cost-sharing/page.tsx:423` — the shared confirm-dialog opener is untyped, forcing an unchecked cast later (`confirmState.tone as "default" | "danger"`). Low impact given few call sites. **Remediation**: add a small `ConfirmConfig` type.

**D18. Debug `console.log` left in production** at `app/login/page.tsx:94`, logging the welcome-email API response client-side. No sensitive data, but unnecessary. Trivial to remove.

**D19. Cosmetic ESLint errors**: two `react/no-unescaped-entities` errors (`app/offline/page.tsx`, `app/trips/[id]/components/TripSetupSheet.tsx`, `app/trips/[id]/packing/personalize/climate/page.tsx`), one `prefer-const` (`usePackingList.ts:180` — moot if D11/dead-code removal proceeds).

**D20. `<img>` used instead of `next/image` in ~15 locations** across `app/trips/[id]/components/*`, `cost-sharing/components/*`, `journal/page.tsx`, `pack-list/`, `features/packing/components/*`, and shared `components/*`. All flagged by ESLint's LCP-warning rule. Notably, this means `next/image`'s server-side image-optimization path (which depends on `sharp`) is never exercised anywhere in the app — a real perf/UX debt item, but also incidentally why the `sharp` CVEs in `npm audit` aren't currently reachable (see Dependency Assessment).

## F. Security / RLS assessment

**Confirmed safe:**
- Service-role key isolation — `SUPABASE_SERVICE_ROLE_KEY` is referenced in exactly one server-only file (`app/api/delete-account/route.ts`); the anon-key client used everywhere else is the intended public-facing credential.
- `delete-account` derives the target user from the caller's own verified bearer token, never a client-supplied ID — no IDOR possible.
- The `trips` list query's client-side `.or()` filter is backed by an independent RLS policy (`user_can_access_trip`) — a crafted request cannot see other users' trips. This is genuine server-side enforcement, not client-side-only filtering.
- RPC grants were tightened in `202506230002_lock_down_rpc_function_grants.sql`: revoked from `public`/`anon`, granted only to `authenticated`; two debug/maintenance functions (`debug_auth_uid()`, `repair_collaborator_members()`) are correctly restricted to `service_role`.
- `.env.local` is git-ignored and not tracked; env var naming (`NEXT_PUBLIC_*` vs unprefixed secrets) correctly reflects what's meant to be public vs private.

**Confirmed vulnerability:**
- D1 — unauthenticated `/api/send-trip-invite` (open relay + HTML injection).

**Likely vulnerabilities:**
- D2 — public journal-images bucket with guessable URLs, undermining the "private" visibility flag.
- D6 — unauthenticated `/api/send-welcome-email` (lower severity, static content).

**Architectural concerns requiring further verification:**
- D7 — several RLS policies and SECURITY DEFINER function bodies exist in production but aren't in tracked migrations, so their caller-privilege checks can't be fully verified from the repo. This is the blocking prerequisite for closing out STORE_READINESS.md's "SECURITY DEFINER functions reviewed one by one" and should happen before further security work in this area.
- No `middleware.ts` / no server-side route gating — noted as an architectural characteristic, not a vulnerability, since no finding here depended on the app shell being gated (RLS is the actual data boundary).

## H. Technical-debt map

- **Duplicated packing implementations** (D11) — the single largest piece of debt found; two divergent data models and business-logic trees for the same feature.
- **Duplicated/conflicting `Trip` type** (D10) between `types/trip.ts` and `app/trips/[id]/types.ts`.
- **Copy-pasted online/offline detection** — reimplemented independently in `OfflineBanner.tsx`, `app/page.tsx`, and `useTripBookings.ts` rather than a shared hook.
- **No shared auth-check pattern** — every protected page independently implements its own "check session → redirect if absent" `useEffect`, rather than a shared hook or centralized guard. Not a security issue (RLS backstops it) but a maintainability one.
- **Schema/migration drift** (D7) — the live Supabase schema is not fully reconstructable from tracked migrations, which is both a security-review blocker and a general "how do we actually know what's in production" gap.
- **Inconsistent `setState`-in-effect pattern** — the same "hydrate local state from localStorage on mount" need is solved two different ways across the packing code: a safe lazy-`useState`-initializer pattern (used correctly for `laundry` in `use-packing-preferences.ts`) and an unsafe effect-based pattern (used everywhere else, ~9 occurrences flagged by React Compiler lint). Only one of the 9 was confirmed to cause an actual user-visible bug (D9), but standardizing on the lazy-initializer pattern would remove the whole class of lint errors and the latent risk in the others.
- **No automated tests** — not a "debt" introduced by any specific change, but worth naming as a standing gap that makes every fix above riskier to verify than it should be.
- **`<img>` instead of `next/image`** (D20) — consistent avoidance across ~15 files; real perf debt (LCP), and incidentally the reason `sharp`'s vulnerable code path is dormant.
